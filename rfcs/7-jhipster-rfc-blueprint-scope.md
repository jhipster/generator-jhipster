# JHipster-RFC-7: Blueprint scope

<!-- This is a RFC template based on the Rust RFC process but simplified: https://github.com/rust-lang/rfcs/ -->

- Feature Name: `blueprint_scope`
- Start Date: 2026-10-13
- Issue: [jhipster/generator-jhipster#35474](https://github.com/jhipster/generator-jhipster/pull/35474)

## Summary

[summary]: #summary

A blueprint belongs to the project it is stored for, in the `blueprints` of its `.yo-rc.json`. The blueprints given to a
generator, by the cli or by the `.yo-rc.json` of its folder, are not inherited by the generators it composes in another
folder, and the `jdl` generator is not blueprinted. `--global-blueprints` gives blueprints to every project a run
generates.

## Motivation

[motivation]: #motivation

A deployment whose `.yo-rc.json` lists a blueprint stored that blueprint in the `.yo-rc.json` of every application of the
workspace, and the next generation of each application composed it: a Spring Boot gateway deployed with the NodeJS
blueprint was generated with the NodeJS blueprint afterwards. The `jdl` generator did the same with the applications of a
jdl, each one getting the blueprints of the folder the jdl was run from, besides the ones its jdl declares.

Three mechanisms combine:

1. The cli passes one `blueprints` option, merging the `--blueprints` of the command line and the `blueprints` of the
   `.yo-rc.json` of the current folder (`cli/environment-builder.ts`, `cli/program.ts`).
2. A blueprinted generator merges the `blueprints` option with the `blueprints` of its own `.yo-rc.json` and stores the
   result there (`generators/base/internal/blueprints-resolver.ts`).
3. `composeWithJHipster` forwards the options of the composing generator, the `blueprints` one included, to the
   generators it composes, in its folder or in another one (`destinationRoot`).

The `jdl` generator, blueprinted itself, also resolved and stored blueprints of its own on top of the ones of the
applications it generates.

## Guide-level explanation

[guide-level-explanation]: #guide-level-explanation

- A project (an application, a deployment, a workspace) uses the blueprints of its `.yo-rc.json`. `--blueprints` on the
  command line adds blueprints to the project the command runs in, and they are stored there.
- A generator composing another one in another folder does not hand it its blueprints: the composed generator uses the
  blueprints of the `.yo-rc.json` of that folder. A generator meaning to apply blueprints there passes them explicitly.
- `--global-blueprints` adds blueprints to every project generated by the run, the ones in other folders included (the
  applications of a jdl or of a workspace, the deployments), each one storing them besides its own:
  `jhipster jdl app.jdl --global-blueprints nodejs`.
- The applications of a jdl use the blueprints their jdl declares (`application { config { blueprints [nodejs] } }`), not
  the ones the `jdl` command is given. A jdl with one application in the current folder still applies `--blueprints` to
  it, the application generator storing them.
- The `jdl` generator is not blueprinted. A blueprint customizing the jdl generation provides a `jdl` generator of its own,
  composing the one of generator-jhipster, and registers it as the `jdl` command of its cli.
- A deployment blueprint customizes the deployment generators (`docker-compose`, `kubernetes`, ...), not the applications
  they deploy.

## Reference-level explanation

[reference-level-explanation]: #reference-level-explanation

- `optionsForAnotherProject` leaves out the `blueprints` and `blueprint` options. `BaseCoreGenerator.composeWithJHipster`
  forwards the options through it when the composed generator has a `destinationRoot` other than the folder of the
  composing generator, the `generatorOptions` given to it still applying.
- `JdlGenerator` extends `BaseCoreGenerator`: no `composeWithBlueprints`, no `delegateTasksToBlueprint`, no blueprints
  resolver. It composes the `bootstrap` generator itself, which commits the files it writes. It generates each application
  of a multi-application jdl in an environment of its own (`env.run`), with the options of `optionsForAnotherProject`.
- The `globalBlueprints` option (`--global-blueprints`) is forwarded across folders: the blueprints resolver merges it with
  the `blueprints` option and the `blueprints` of the `.yo-rc.json`, storing the result, and the `jdl` generator hands it
  to the applications it generates. The cli reads `--global-blueprints` from the command line, like `--blueprints`, to look
  the packages up in the environment of each application.
- The environment of each application still looks up the blueprints of the current folder of the process and of the
  command line: that only registers packages, nothing is composed or stored without the option or the configuration.

## Drawbacks

[drawbacks]: #drawbacks

- `jhipster jdl app.jdl --blueprints foo` no longer applies `foo` to every application of a multi-application jdl: the
  jdl declares the blueprints of each application, or `--global-blueprints foo` gives it to all of them.
- A blueprint providing a `jdl` sub-generator is no longer composed by the `jdl` command; none of the official blueprints
  has one.
- A blueprint generator that composed a generator of generator-jhipster in another folder, expecting its blueprints to be
  applied there, has to pass them.

## Rationale and alternatives

[rationale-and-alternatives]: #rationale-and-alternatives

- Dropping the blueprints at each call site composing into another folder (the first version of #35474, for the
  workspaces): it fixes one path at a time, and each new generator composing into another folder repeats the problem.
- The cli passing only the command line blueprints as the `blueprints` option, the ones of the `.yo-rc.json` being read by
  each generator from its own configuration: it stops the blueprints of the current folder from leaking, but an explicit
  `--blueprints` still reaches every project composed into. It may still be done, independently.
- Keeping the `jdl` generator blueprinted: its blueprints resolver mixes the blueprints of the folder it runs in with the
  ones of the applications it generates, the confusing part this RFC removes. The blueprints of the applications are only
  known once the jdl is read: they could not blueprint the generator reading it anyway.

## Prior art

[prior-art]: #prior-art

- The jdl already declares blueprints per application (`blueprints [...]` and `config(<blueprint>)`), stored in the
  `.yo-rc.json` of each application.

## Unresolved questions

[unresolved-questions]: #unresolved-questions

- Whether the cli should keep merging the blueprints of the `.yo-rc.json` of the current folder into the `blueprints`
  option.

## Future possibilities

[future-possibilities]: #future-possibilities

- Other generators orchestrating several projects (`workspaces`, `deployment`) could move to `BaseCoreGenerator` the same
  way, leaving the blueprints to the projects.
